## 🧠 Что такое Git и зачем он нужен

**Git** — это система контроля версий. Простыми словами, это машина времени для вашего кода.

| Понятие | Аналогия | Что это |
|---|---|---|
| **Репозиторий** | Флешка с сохранениями | Папка, в которой Git хранит всю историю вашего кода |
| **Коммит (commit)** | Точка сохранения в игре | Снимок вашего кода в конкретный момент времени |
| **Ветка (branch)** | Альтернативное прохождение | Параллельная версия кода для экспериментов |
| **Push** | Загрузить флешку в облако | Отправить коммиты на сервер (GitHub) |
| **Pull** | Скачать с облака на флешку | Забрать чужие изменения с сервера |
| **GitHub** | Облачное хранилище | Сайт, где хранятся ваши репозитории в интернете |

**Зачем это нужно:**
- 💾 **Бэкап:** Код хранится на сервере. Компьютер сломался — код не пропал.
- ⏪ **Откат:** Написали ерунду? Можно вернуться к любому предыдущему коммиту.
- 👥 **Командная работа:** Несколько человек могут работать над одним проектом одновременно.
- 📝 **История:** Вы всегда можете посмотреть, кто, когда и что изменил.

## 📥 Шаг 1. Установка Git

### Что делаем:
1. Откройте сайт [git-scm.com/downloads](https://git-scm.com/downloads)
2. Скачайте версию для вашей ОС (Windows / macOS / Linux)
3. Запустите установщик
4. **На всех этапах нажимайте «Next» (Далее), оставляя настройки по умолчанию**
5. Перезагрузите компьютер (желательно)

### Почему именно так:
- **Git — это отдельная программа**, которая устанавливается на ваш компьютер. VS Code будет «общаться» с ней через кнопки, но сама программа Git должна быть установлена.
- **Почему «Next» на всех этапах?** Настройки по умолчанию оптимальны для 99% пользователей. Git предложит выбрать редактор (Vim, Nano), но это не важно — мы работаем через VS Code.
- При установке Git добавляет себя в системный PATH — это «адресная книга» операционной системы, где прописаны пути ко всем программам. Благодаря этому VS Code сможет найти Git и работать с ним.

### Как проверить, что Git установился:
Откройте терминал (командную строку) и введите:
```bash
git --version
```
Если видите что-то вроде `git version 2.45.0` — всё работает. Если «команда не найдена» — перезагрузите компьютер и попробуйте снова.

## ⚙️ Шаг 3. Первая настройка Git (делается один раз!)

### Что делаем:
Откройте VS Code, откройте терминал (`Ctrl` + `` ` `` или меню `Terminal → New Terminal`) и введите:

```bash
git config --global user.name "Ваше Имя Фамилия"
git config --global user.email "ваша_почта@example.com"
```

### Почему это нужно:
**Каждый коммит в Git подписывается автором.** Это как штамп «Сделал Иванов И.И., 15.09.2026» на каждом сохранении.

- `user.name` — имя, которое будет отображаться в истории коммитов
- `user.email` — ваш уникальный идентификатор. GitHub по email сопоставляет коммиты с вашим аккаунтом и показывает вашу аватарку
- `--global` — означает «применить ко ВСЕМ проектам на этом компьютере». Вам не придётся повторять это для каждого нового проекта

### Почему email должен совпадать с GitHub:
Если email в Git и на GitHub разные, GitHub не поймёт, что коммиты ваши, и не покажет вашу аватарку и вклад в репозиторий.

## 🗑 Шаг 4. Создание `.gitignore` (ОБЯЗАТЕЛЬНО!)

### Что делаем:
1. В VS Code откройте папку с вашим проектом (`File → Open Folder`)
2. В левой панели (Explorer) создайте новый файл с именем **`.gitignore`** (обязательно с точкой в начале!)
3. Вставьте туда этот текст:

```text
# Виртуальные окружения Python
venv/
.venv/
env/

# Кэш и скомпилированные файлы Python
__pycache__/
*.pyc
*.pyo

# Секреты и переменные окружения
.env

# Настройки IDE
.idea/
.vscode/
.DS_Store
```

4. Сохраните файл (`Ctrl + S`)

### Почему это критически важно:
**Не все файлы должны попадать в Git.** В вашем Python-проекте есть три категории «мусора»:

**1. Автоматически генерируемые файлы (`__pycache__/`, `*.pyc`)**
Python при запуске создаёт скомпилированные версии файлов. Они генерируются заново каждый раз и не нужны в репозитории.

**2. Файлы, привязанные к вашему компьютеру (`venv/`)**
Папка `venv` — это виртуальное окружение с установленными библиотеками. Она может весить 500+ МБ и содержать тысячи файлов. Если вы запушите её:
- Репозиторий раздуется до гигантских размеров
- GitHub может отклонить пуш (лимит 100 МБ на файл)
- Ваш коллега не сможет использовать ваше `venv`, потому что пути зависят от вашей ОС

Вместо этого коммитьте файл `requirements.txt` (список библиотек), а коллега сам создаст своё `venv` командой `pip install -r requirements.txt`.

**3. Файлы с секретами (`.env`)**
Файл `.env` содержит пароли, API-ключи, токены. Если вы запушите его на GitHub — **любой человек в интернете** увидит ваши пароли. Боты сканируют GitHub и взламывают аккаунты за минуты. Даже если вы удалите файл следующим коммитом, он останется в истории Git навсегда.

### Почему точка в начале имени `.gitignore`:
В Unix-системах (Linux, macOS) файлы с точкой в начале считаются скрытыми/конфигурационными. Это соглашение означает: «Это не файл проекта, это настройка для инструмента».

### Как работает `.gitignore`:
Git читает этот файл **перед тем**, как показать вам список изменений. Если в `.gitignore` написано `venv/`, Git полностью игнорирует эту папку — он её не видит.

### Что означают символы:
| Запись | Что означает |
|---|---|
| `venv/` | Слэш в конце = «это папка». Git проигнорирует папку и всё внутри |
| `*.pyc` | Звёздочка = «любое имя». Git проигнорирует все файлы с расширением `.pyc` |
| `.env` | Точное совпадение. Git проигнорирует только файл с именем `.env` |

## 🏗 Шаг 5. Инициализация репозитория

### Что делаем:
1. В VS Code нажмите на иконку **Source Control** (веточка) на самой левой панели
2. В центре экрана появится кнопка **«Initialize Repository»**
3. Нажмите её и выберите папку с вашим проектом

### Почему это нужно:
До этого момента Git не знал о вашем проекте. У вас есть папка с файлами, но Git её не отслеживает. Инициализация говорит Git: «Начни следить за этой папкой».

### Что происходит под капотом:
Git создаёт в вашей папке **скрытую папку `.git`**. Это «мозг» репозитория. В ней хранится:
- Вся история коммитов
- Информация о ветках
- Индекс (список файлов, подготовленных к коммиту)
- Конфигурация репозитория

**Вам никогда не нужно заходить в папку `.git` вручную.** Если вы её удалите — удалится вся история Git, но ваши файлы останутся.

### Что вы увидите после инициализации:
В панели Source Control все ваши файлы появятся зелёным цветом с буквой **U** (Untracked). Это значит: «Git видит эти файлы, но ещё не следит за ними». Файлы из `.gitignore` (например, `venv/`) не появятся вообще — Git их игнорирует.

## 📸 Шаг 6. Добавление файлов и первый коммит

### Что делаем:

#### Визуально (через VS Code):
1. Откройте панель **Source Control** (веточка слева)
2. Вы увидите блок **Changes** со списком файлов
3. Наведите курсор на заголовок **Changes** и нажмите **`+`** (плюс)
4. Все файлы переместятся в блок **Staged Changes**
5. В поле **Message** сверху напишите: `Первый коммит: базовый код проекта`
6. Нажмите кнопку **Commit**

#### Через терминал:
```bash
git add .
git commit -m "Первый коммит: базовый код проекта"
```

### Почему два этапа (add + commit), а не одна кнопка «Сохранить»:

**Аналогия с групповым фото:**
- `git add` (кнопка `+`) — вы просите людей сесть на стулья и подготовиться. Кто-то сел, кто-то ещё стоит.
- `git commit` — фотограф нажимает кнопку. На фото попадают только те, кто сидел на стульях.

**Зачем это нужно?** Чтобы вы могли делать **разные коммиты из разных изменений**.

**Пример:** Вы написали новую функцию и исправили опечатку в комментарии. Это два разных изменения:
1. Нажимаете `+` только рядом с файлом новой функции → пишете «Добавил функцию расчёта скидки» → Commit
2. Нажимаете `+` рядом с файлом с исправленной опечаткой → пишете «Исправил опечатку» → Commit

Теперь у вас два чистых, осмысленных коммита. Если функция сломается, вы сможете откатить только её, не трогая исправление опечатки.

### Что означает точка в `git add .`:
Точка (`.`) означает «текущая папка». Git рекурсивно обойдёт все подпапки и добавит все файлы. Это самый быстрый способ добавить всё сразу.

### Что происходит при коммите:
Git делает «снимок» (snapshot) всех файлов из Staged Changes и сохраняет его в историю с вашим сообщением. Этот снимок получает уникальный хэш (например, `a3f5b2c`), по которому его можно найти в истории.

### Почему важно писать осмысленные сообщения:
Через месяц вы забудете, что делали.

| ❌ Плохо | ✅ Хорошо |
|---|---|
| `fix` | `Исправил баг с делением на ноль` |
| `asdf` | `Добавил парсинг сайта example.com` |
| `обновил код` | `Обновил библиотеку requests до 2.28.0` |
| `123` | `Добавил функцию расчёта скидки` |

## ☁️ Шаг 7. Создание репозитория на GitHub

### Что делаем:
1. Зайдите на [github.com](https://github.com/) и войдите в аккаунт
2. Нажмите **«New»** (или `+ → New repository`)
3. Введите имя репозитория (Repository name)
4. ⛔ **НЕ ставьте галочки** «Add a README file» и «Add .gitignore»
5. Нажмите **Create repository**
6. Скопируйте ссылку, которая заканчивается на `.git` (например, `https://github.com/username/my-project.git`)

### Почему репозиторий должен быть пустым:
Это **критически важный момент**, на котором спотыкаются 90% новичков.

Если вы поставите галочку «Add a README», GitHub создаст на сервере репозиторий с **одним коммитом** (файл README.md).

У вас на компьютере уже есть репозиторий с **одним коммитом** (ваш «Первый коммит»).

Когда вы попытаетесь запушить, Git скажет:
> «У тебя на компьютере один коммит, а на сервере — другой. Они не связаны. Я не знаю, как их объединить».

Это называется **конфликт историй**. Две разные истории коммитов, и Git не знает, как их слить.

**Решение:** создавайте на GitHub **пустой** репозиторий. Тогда на сервере не будет коммитов, и вы спокойно запушите свою историю.

### Почему ссылка заканчивается на `.git`:
Это протокол Git. Эта ссылка — «адрес» вашего репозитория на сервере, по которому Git будет отправлять и получать данные.

## 🔗 Шаг 8. Связывание с GitHub и первый пуш

### Что делаем:
Откройте терминал в VS Code (`Ctrl` + `` ` ``) и выполните три команды:

```bash
git remote add origin https://github.com/ВАШ_ЛОГИН/ВАШ_РЕПО.git
git branch -M main
git push -u origin main
```

### Разбор каждой команды:

#### `git remote add origin https://...`
- `remote` — удалённый репозиторий (сервер в интернете)
- `add` — добавить новый
- `origin` — **кличка** (алиас) для сервера. Вы могли бы назвать его «github» или «server», но по соглашению все называют его «origin»
- `https://...` — адрес вашего репозитория

**Почему нужна кличка?** Чтобы не писать каждый раз длинную ссылку. Вместо `git push https://github.com/ваш-логин/ваш-репо.git main` вы пишете `git push origin main`.

#### `git branch -M main`
- `branch` — работа с ветками
- `-M` — переименовать текущую ветку
- `main` — новое имя

**Почему `main`, а не `master`?** Раньше главная ветка называлась `master`. С 2020 года GitHub и другие платформы перешли на `main` как более нейтральный термин. Сейчас `main` — стандарт.

**Зачем переименовывать?** Когда вы сделали `git init`, Git создал ветку с именем по умолчанию (обычно `master`). На GitHub главная ветка — `main`. Чтобы не было путаницы, переименовываем.

#### `git push -u origin main`
- `push` — отправить коммиты на сервер
- `origin` — на сервер, который мы зарегистрировали выше
- `main` — в ветку `main`
- `-u` (или `--set-upstream`) — **«запомни эту связь»**

**Что делает `-u`?** Вы говорите Git: «Запомни, что моя локальная ветка `main` всегда связана с веткой `main` на сервере `origin`». После этого в следующий раз достаточно просто `git push` без дополнительных флагов.

**Почему без `-u` будет ошибка?** При первом пуше Git не знает, в какую ветку на сервере отправлять код. Без `-u` вы получите ошибку: `fatal: The current branch main has no upstream branch`.

## 🔄 Шаг 9. Ваш ежедневный ритуал

Каждый раз, когда вы поработали над кодом:

### Визуально (VS Code):
1. 💻 Написали код
2. 💾 Сохранили файл (`Ctrl + S`)
3. 🔀 Открыли панель **Source Control** (веточка слева)
4. ➕ Нажали **`+`** рядом с Changes
5. ✍️ Написали сообщение в поле Message
6. ✅ Нажали **Commit**
7. 🔄 Нажали **Sync** (кнопка внизу слева) — это сделает Push

### Через терминал:
```bash
git add .
git commit -m "Понятное описание того, что сделано"
git push
```

### Почему Sync вместо Push:
Кнопка **Sync** делает два действия:
1. **Pull** — скачивает изменения с GitHub (если кто-то другой что-то запушил)
2. **Push** — отправляет ваши изменения на GitHub

Это удобно, потому что одним кликом вы синхронизируете локальную копию с сервером.

## 🦸 Суперспособности VS Code для Git

### 1. Просмотр изменений (Diff View) 🔥
В панели Source Control **кликните на любой изменённый файл**. Откроется экран:
- **Слева (красным):** как код выглядел раньше
- **Справа (зелёным):** как код выглядит сейчас

**Зачем:** Вы забыли, что меняли вчера? Открыли Diff View и вспомнили. Хотите проверить, не удалили ли случайно важную строчку? Diff View покажет.

### 2. Нижняя панель статуса
В самом низу окна VS Code (синяя полоска):
- **Слева** — название текущей ветки (например, `main`). Кликните, чтобы переключиться на другую ветку
- **Кнопка Sync (🔄)** — синхронизация одним кликом

### 3. Отмена последнего коммита
Если сделали коммит и поняли, что ошиблись:
1. Нажмите **три точки (`...`)** в панели Source Control
2. Выберите **Commit → Undo Last Commit**
3. Ваши файлы вернутся в состояние «подготовлено к коммиту», ничего не потеряется

**Когда полезно:** написали плохое сообщение, забыли добавить файл, случайно закоммитили не то.

## 🎨 Цвета файлов в VS Code: что они означают

| Цвет | Буква | Статус | Что значит | Что делать |
|---|---|---|---|---|
| 🟢 Зелёный | U | Untracked | Новый файл, Git его видит впервые | Нажмите `+` чтобы добавить |
| 🟡 Жёлтый / 🔵 Синий | M | Modified | Файл уже был в Git, но вы его изменили | Нажмите `+` чтобы добавить изменения |
| 🔴 Красный | D | Deleted | Вы удалили файл, который Git отслеживал | Нажмите `+` чтобы зафиксировать удаление |
| ⚪ Серый | — | Ignored | Файл в `.gitignore`, Git его не видит | Ничего, так и должно быть |

**Все эти файлы (зелёные, жёлтые, красные) попадут в коммит**, когда вы нажмёте `+` и сделаете Commit.

## 🆘 Частые ошибки и решения (FAQ)

### ❓ «Nothing specified, nothing added»
**Что значит:** Git не нашёл файлов для добавления или коммита.

**Причины и решения:**
1. **Нет изменений** — вы не меняли код с последнего коммита. Измените файл, сохраните (`Ctrl + S`), попробуйте снова.
2. **Все файлы в `.gitignore`** — откройте `.gitignore` и проверьте, нет ли там строк `*` или `*.py`, которые игнорируют всё.
3. **Вы не в той папке** — убедитесь, что терминал открыт в корне проекта.

---

### ❓ `fatal: The current branch main has no upstream branch`
**Что значит:** Git не знает, в какую ветку на сервере пушить.

**Решение:**
```bash
git push --set-upstream origin main
```
Или короче:
```bash
git push -u origin main
```
Это нужно сделать только один раз. После этого `git push` будет работать без флагов.

---

### ❓ «Я нажал Commit, но на GitHub код не появился!»
**Что значит:** Вы сделали коммит, но забыли сделать Push.

**Почему:** Commit сохраняет изменения **только на вашем компьютере**. Чтобы они попали на GitHub, нужен Push.

**Решение:** Нажмите кнопку **Sync (🔄)** внизу слева или три точки (`...`) → **Push**.

---

### ❓ «Кнопка Push не работает, VS Code ругается»
**Что значит:** Кто-то (или вы с другого ПК) уже запушил изменения на GitHub. Git не даст вам пушить, чтобы не затереть чужое.

**Решение:** Сначала нажмите **Pull** (или Sync), чтобы скачать чужие изменения, а потом делайте Push.

---

### ❓ «Я случайно закоммитил папку `venv` или файл `.env`!»
**Что делать:**

1. **Если ещё не сделали Push:**
   - Нажмите три точки (`...`) → **Commit → Undo Last Commit**
   - Добавьте папку/файл в `.gitignore`
   - Сделайте коммит заново

2. **Если уже сделали Push:**
   - ⚠️ **Срочно меняйте пароли**, если в `.env` были секреты! Они остались в истории Git навсегда.
   - Выполните в терминале:
   ```bash
   git rm -r --cached venv/
   git rm --cached .env
   git commit -m "Убрал мусор из репозитория"
   git push
   ```

---

### ❓ «Я сделал `git add .`, но некоторые файлы не добавились»
**Что значит:** Эти файлы указаны в `.gitignore`.

**Решение:** Откройте `.gitignore` и уберите строки, которые игнорируют нужные вам файлы.

---

### ❓ «Кириллица в именах папок отображается как `\320\270\321\201...`»
**Что значит:** Git по умолчанию кодирует не-ASCII символы (кириллицу) в виде escape-последовательностей.

**Это нормально!** На GitHub названия будут читаемыми. Чтобы исправить отображение в терминале:
```bash
git config --global core.quotepath false
```

---

### ❓ «Я написал `git comit` и Git ругается»
**Что значит:** Опечатка в команде.

**Правильно:** `git commit` (с двумя буквами `m`).

---

### ❓ «На GitHub нет моих папок, хотя я всё запушил»
**Что значит:** Git **не хранит пустые папки**. Если в папке нет ни одного файла, Git её не создаст в репозитории.

**Решение:** Добавьте в пустую папку файл-заглушку `.gitkeep`:
```bash
touch пустая_папка/.gitkeep
git add .
git commit -m "Добавил .gitkeep для сохранения структуры папок"
git push
```

## 📋 Шпаргалка команд

| Команда | Что делает |
|---|---|
| `git init` | Инициализировать репозиторий (создать папку `.git`) |
| `git status` | Показать статус: что изменилось, что добавлено, что готово к коммиту. **Ваш лучший друг!** |
| `git add .` | Добавить все файлы из текущей папки и подпапок в зону подготовки |
| `git add файл.py` | Добавить конкретный файл |
| `git commit -m "сообщение"` | Создать коммит (точку сохранения) |
| `git push` | Отправить коммиты на GitHub |
| `git push -u origin main` | Первый пуш с установкой связи |
| `git pull` | Скачать изменения с GitHub на компьютер |
| `git log` | Показать историю коммитов |
| `git diff` | Показать, какие строчки кода изменились |
| `git remote add origin URL` | Связать локальный репозиторий с GitHub |
| `git branch -M main` | Переименовать текущую ветку в `main` |
| `git restore --staged файл` | Убрать файл из зоны подготовки (отменить `git add`) |
| `git rm --cached файл` | Убрать файл из Git, но оставить на диске |
| `git config --global user.name "Имя"` | Установить имя автора коммитов |
| `git config --global user.email "email"` | Установить email автора коммитов |
| `git config --global core.quotepath false` | Показывать кириллицу нормально в терминале |

## 💡 Золотые правила

1. **Коммитьте часто.** Лучше 5 маленьких коммитов, чем один огромный раз в неделю.
2. **Пишите осмысленные сообщения.** `"fix"` — плохо. `"Исправил ошибку в расчёте скидки"` — хорошо.
3. **Всегда проверяйте `git status`** перед коммитом. Читайте, что Git вам показывает.
4. **Никогда не коммитьте пароли, токены и `.env`.** Если запушили — меняйте пароли немедленно.
5. **Не коммитьте `venv/`.** Используйте `requirements.txt` вместо этого.
6. **Если что-то сломалось — не паникуйте.** Git почти всегда можно откатить. Спросите у преподавателя или погуглите ошибку.

---

> 📌 **Помните:** Git — это не магия, а инструмент. Чем чаще вы его используете, тем проще он становится. Через неделю `git add . → git commit → git push` станет таким же автоматическим, как `Ctrl + S`.
